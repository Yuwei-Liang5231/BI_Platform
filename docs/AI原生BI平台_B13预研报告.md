# AI 原生 BI 平台 B13 自动建模——预研报告（B13-1 Spike）

> 日期：2026-09-17 ｜ 执行方案第十一节 B13-1 ｜ 结论：**可行，建议进入 B13-2 实施（确认流向导）**

## 一、背景与目标

用户上传数据集后，表关系与指标目前完全手工配置（B1/B2）。B13 目标：平台自动**建议**
表关系与指标候选，人工确认后才入库——"只出建议不自动入库"是铁律（架构 7.11）。

本预研 spike 的任务：实现建议引擎原型 + 对 S1 两套合成数据（A 电商零售 / B SaaS 订阅，
共 8 表 41.5 万行）实跑验证，回答三个问题：

1. 已知真实关系的**召回率**能到多少？
2. 误报长什么样、能否靠证据+人工确认兜住？
3. 哪些场景**必须人工**，自动化边界画在哪？

## 二、引擎设计（已实现，`app/domain/modeling/`）

**表关系建议**（可解释打分，非黑盒）：
- 候选列：文本列且基数 ≤ 5000（与拆解维度同一护栏）；
- 值域重叠 = 两列 distinct 交集 / 较小侧基数（DuckDB 现算）；
- 命名相似 = 归一化相等 1.0 / 包含 0.7 / 词元 Jaccard；
- 综合分 = 0.6×重叠 + 0.4×命名；双低（重叠<0.5 且命名≠1.0）不输出；
- 方向按基数定 many_to_one；每对列留最高分；已登记关系标注 `existing`。

**指标候选**：日期列 × 数值列 → sum；高基数文本列（>100）→ count_distinct；
可选 LLM 辅助提议中文指标名（输出锚定真实表列，非法丢弃）。

**API**：`POST /api/modeling/suggestions`（只读，零副作用）。

## 三、实跑结果（`backend/scripts/b13_pilot.py` 可重跑，结果 `docs/b13_pilot_result.json`）

### 3.1 表关系：ground truth 6 条 → 检出 5 条，误报 2 条

| 引擎建议 | 判定 | 说明 |
|---|---|---|
| channels.channel_id → orders.channel_id | ✅ 真实 | overlap 1.0 / name 1.0 |
| products.product_id → orders.product_id | ✅ 真实 | 同上 |
| plans.plan_id → subscriptions.plan_id | ✅ 真实 | 同上 |
| accounts.account_id → subscriptions.account_id | ✅ 真实 | 同上 |
| accounts.account_id → usage_events.account_id | ✅ 真实 | 同上 |
| **orders.user_id → users.user_id** | ❌ **漏检** | 两侧基数 12500 > 5000 护栏，被采样排除 |
| users.region → accounts.region（跨行业） | ⚠️ 误报 | 值域巧合相同（枚举地区）；分项全 1.0——纯值域+命名无法区分 |
| subscriptions.billing_cycle → plans.billing_unit | ⚠️ 边界 | overlap 1.0 / name 0.33（"月付/年付"枚举巧合），0.73 分踩线 |

**关系召回 5/6（83%），前 5 条精度 100%，全量精度 5/7（71%）**——两个误报都是"枚举值域
巧合"这一类，且分数特征明显（billing_cycle 踩线、region 靠 LLM 语义层可过滤）。

### 3.2 指标候选：26 条，可用率约 60%

有效：pay_amount/refund_amount/mrr_amount/usage_count/duration_min 合计、
order_id/account_id/subscription_id 数等（约 16 条）。
噪音：level（等级列）sum、auto_renew（0/1 标志）sum、外键列重复 count_distinct 等——
可由 LLM 辅助命名时过滤（"标志列不建议 sum"），或人工在确认流中勾选。

### 3.3 漏检根因（重要发现）

user_id 基数 12500 超出 5000 护栏 → 两侧都不参与值域采样 → 漏检。**真实业务里
高基数键（用户 ID、订单号）恰恰最常见**，护栏必须为关系建议单独放宽。

## 四、可行性结论

**可行，建议按以下修正进入 B13-2**：

1. **关系建议增加"高基数兜底"**：护栏外列不做全量值域对比，改为**截断采样**
   （各取前 N 万个值估算重叠率，结果标注 sampled=true 置信降级）——可修复 user_id 漏检；
2. **跨数据集枚举巧合误报**：加两条抑制规则——①两列所在数据集无任何其他强关联时
   降权（孤立巧合）；②进 LLM 语义复审（可选，利用既有 LLM 配置判断"这两列是否业务同一实体"）；
3. **指标候选噪音**：标志列（布尔/0-1）、枚举/等级列排除 sum 候选；LLM 辅助命名顺带过滤；
4. **确认流向导（B12-2 已有成熟模式可复用）**：建议列表（含证据分）→ 人工勾选 →
   走既有 POST /datasets/{id}/relations 与 POST /metrics 接口入库——**零新增写路径**，
   全部复用已冻结契约，实施风险低、工作量约 1 个子批。

## 五、哪些场景必须人工（自动化边界）

| 场景 | 为什么必须人工 |
|---|---|
| 跨行业/跨主题的同枚举列（如两个不同业务的 region） | 值域+命名无法区分巧合与真实关联 |
| 复合键关系（两列联合才能唯一定位） | 单列重叠率天然偏低，自动判定不可靠 |
| 关系类型歧义（1:1 / 多对多） | 引擎固定输出 many_to_one，语义需人判断 |
| 指标口径的业务含义（"退款金额"还是"退款笔数"） | 引擎只知列名与类型，业务语义必须人给 |
| 汇率/比率类指标 | 组合分子分母的选择是口径决策 |
| 数据质量存疑的列（混杂内容、全空） | 质检报告（B8）应先于建模建议被消费 |

## 七、遗留与 Non-goal

- LLM 辅助语义复审未在 pilot 中实跑（test 环境无 LLM 配置）——B12-2 的占位符审计
  模式可直接复用于"提议合法性校验"，B13-2 落地时补 mock 用例；
- 复合键、1:1、多对多关系检测——Non-goal（见第五节，必须人工）；
- 自动建模不做任何静默写入——B13-2 确认流是唯一入库通道。
