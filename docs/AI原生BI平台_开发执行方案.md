### 关于第 1 项的重要补充：行业无关性是硬约束

你的要求"支持各种业务数据，而非仅电商"是一个**架构级约束**，不只是数据问题。我的落实方式：

1. **写入不变式 7**：行业语义只允许通过两层表达——数据层（`datasets` / `dataset_relations` / `dataset_coverage`）与配置层（`calc_rule`、指标模板、`topic` 枚举）。编译器、取数服务、元数据模型中**禁止任何行业分支、行业专属字段或硬编码业务规则**。
2. **合成数据不能只用电商**。只用一套电商数据验证，等于只证明了"电商能跑通"，无法暴露行业适配缺陷。我生成**两套结构差异显著**的数据集：

| 数据集 | 行业形态 | 表结构 | 刻意制造的差异 |
|---|---|---|---|
| **A 零售交易型** | 电商零售 | orders / users / products / channels | 订单粒度、退款与满减、品类×区域维度 |
| **B 订阅服务型** | SaaS | subscriptions / accounts / plans / usage_events | 订阅周期、经常性收入、账户粒度、无"订单"概念 |

3. **验收看差异而非看数量**：同一套编译器在 A/B 上独立完成"定义 → 编译 → 取数 → 导出"，**不修改任何产品代码**。若 B 的订阅周期类语义超出 v1 算子，必须被**明确拒绝并提示**，而不是静默算出错误结果——这恰好能在阶段 1 早期验证算子清单的边界。
4. 两套数据都包含 **GBK 编码样本与混杂类型列**，顺带验证接入质检。

## 三、我的开发原则

| 原则 | 具体做法 |
|---|---|
| **可运行优先于完整** | 每批次结束必须能启动、能请求、能看到结果；不做"写了一半的模块" |
| **测试先行于编译器** | 指标编译器是全项目核心难点，先写 golden SQL 测试用例（定义 → 期望 SQL），再写实现 |
| **契约先于实现** | 先冻结 `ApiResponse` 与接口清单（含 HTTP 码与 body code 对齐），前后端据此并行 |
| **依赖驱动排序** | 数据接入 → 指标元数据 → 编译器 → 取数服务 → 权限 → 前端。页面最后做 |
| **不交付未验证的代码** | 每批次我都实际用 Bash 跑通 `pytest` 与启动冒烟，再交付给你 |
| **每批有可验看清单** | 交付时明确告诉你"打开哪个页面、点什么、应该看到什么"，你能自己确认 |
| **不替业务做决策** | 口径定义、仲裁、验收结论由业务方出；我只提供工具与默认值 |
| **行业无关是硬约束** | 合成数据只是验证载体。任何行业语义不得进入编译器、取数服务、元数据模型；每涉及行业相关逻辑，我都用 A/B 两套数据集交叉验证 |
