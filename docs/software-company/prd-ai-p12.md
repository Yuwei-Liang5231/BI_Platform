# PRD：AI 原生 BI 平台 — AI 能力扩展（增量 P1+P2）

> 文档类型：增量 PRD（简单版）｜产品经理：许清楚
> 范围：本次聚焦 **AI 缺位域**的六项能力扩展，不重复建设已覆盖域。
> 配套代码基线：`bi-platform/`（后端 `backend/` FastAPI+SQLAlchemy+SQLite+DuckDB；前端 `web/` Vue3+Element Plus+Pinia+Vite）

---

## 0. 范围边界（已评审确认，避免重复建设）

**AI 已覆盖域（本次不动）：**
- 报告中心：LLM 叙述层 `backend/app/domain/report/narrative.py`，算写分离——LLM 只见 `{{ref:KEY}}` 占位符，三道审计（`_audit_sentence`）剔句/降级规则句。
- 问数 Agent：`backend/app/domain/ask/service.py`，LLM 意图解析、越纲字段丢弃防幻觉、逃生舱对话兜底、空态推荐问题（后端按可见指标生成）。
- 建模建议：`backend/app/domain/modeling/service.py`（`_llm_relation_review` / `_llm_metric_candidates`），LLM 语义复审 + 指标候选，输出锚定真实列名防幻觉。
- 模型管理页：`llm_models` 表 CRUD/互斥/连通测试；LLM 配置多通道（`llm_models is_active=1` > env 兜底 > 无 LLM 则全部降级规则句）。

**AI 缺位域（本次要补的四个场景 + 六项能力）：**
数据看板、异动检测+通知、归因下钻、指标创建、数据集接入、问数空态推荐。

## 1. 背景与目标

### 1.1 背景
平台已在「报告生成、问数对话、建模建议、模型管理」四域用 LLM 提升了效率，并沉淀了**算写分离**这一核心设施（`narrative.py` 的占位符+预格式化回填+三道审计）与 **LLM 可选降级**的成熟范式（模型管理页配置通道）。但业务用户在「看板消费、异动解读、口径编写、数据接入、主动推荐、归因理解」六个日常触点上仍缺乏 AI 辅助——这些触点目前是纯规则/纯人工，体验断层明显。

### 1.2 产品目标
把 AI 能力从「创作端（报告/问数/建模）」延伸到「消费端与分析辅助端」，让用户：
1. 一眼看懂看板（AI 速览替代逐卡阅读）；
2. 异动发生时不仅知「是什么」更知「可能为什么」（业务假设）；
3. 建指标/接数据时有人帮写口径与标含义，降低建模门槛；
4. 问数入口从「静态示例」升级为「感知当前业务动态的主动推荐」；
5. 下钻归因结果有 AI 一句话点题。

### 1.3 成功指标（建议，非硬验收）
- 看板页「AI 速览」点击/展开率、指标详情页异动假设与归因解读的曝光率；
- 指标创建流程中口径助手采纳率；
- 问数空态动态推荐的问句发起转化率。

### 1.4 两条不可让步的红线（贯穿全部六项）
- **算写分离**：LLM 永远不见原始数字——占位符 + 服务端预格式化回填 + 裸数字审计。任何**叙述类**新 LLM 调用点必须遵守。
- **LLM 可选**：LLM 未配置/失败时所有新功能必须优雅降级，不得破坏现有无 LLM 体验（公司网络屏蔽外网 LLM，用户大概率跑在降级态）。

## 2. 用户故事

### 功能 1：看板智能摘要（AI 速览）
- 作为运营负责人，我在看板页希望看到一个 3~5 句的「AI 速览」，概括当前周期内各指标的关键走势，而不必逐个卡片阅读。
- 作为分析师，我希望速览中的数字与卡片完全一致、可逐项对账，且 LLM 未配置时该区块自动隐藏或降级为一句规则概述，不影响看板本身。

### 功能 2：异动 AI 假设解释
- 作为业务 owner，当某指标触发异动通知，我希望除固定建议动作外，还能看到一段基于「常用维度拆解事实」的业务假设（如主贡献维度、方向是否一致），帮我快速定位排查方向。
- 作为分析师，我希望该假设严格基于平台已算出的拆解事实、绝不编造数字，并在指标详情页异动处直接看到。

### 功能 3：指标口径 AI 助手
- 作为指标创建者，我在建指标时希望 AI 根据「数据集列名 + 样本值」帮我想一个名称、别名和 `calc_notes` 草稿（为什么这样定/其他算法适用场景/易错点），我再采纳或编辑。
- 作为数据治理者，我希望 AI 建议仅供参考、绝不自动入库，最终口径由我确认。

### 功能 4：数据集字段语义标注
- 作为建模者，数据集上传后我希望 AI 按「列名 + 样本值」给每列一个业务含义备注，供关系向导与指标建议消费，减少我手动填备注的成本。
- 作为下游用户，我希望这些标注能提升建模建议与关系复审的准确性。

### 功能 5：问数主动推荐升级
- 作为新用户，进入问数空态时我希望看到的推荐问题不是千篇一律的模板，而是结合「最近异动/趋势」的动态问题（如「近 7 天日销售额突增，点击查看按渠道拆解」），更容易上手。
- 作为老用户，我希望推荐文案不直接暴露未回填的原始数字，数字由服务端预格式化。

### 功能 6：归因下钻 AI 解读
- 作为分析师，在下钻树结果处我希望加一句占位符化的 AI 解读，点出本层变化的主要贡献来源，辅助我快速理解下钻结论。
- 作为读者，我希望该解读与我看到的拆解数字完全一致，且 LLM 不可用时整句不显示、不影响下钻结果。

## 3. 需求池（优先级建议）

> 说明：用户已确认六项全部交付，分两批（P1 批先行：#1/#2/#3；P2 批：#4/#5/#6）。下方 P0/P1/P2 表示**实现优先级与风险排序**（P0=本迭代必做先行、复用已验证设施、痛点最直接；P1=重要、依赖关系强；P2=增强型、价值最小可收尾），不代表可裁剪。

| 编号 | 功能 | 建议优先级 | 理由 |
|---|---|---|---|
| #1 | 看板智能摘要 | **P0** | 直接复用 `narrative.py` 已验证的算写分离设施（`_build_ref_table`/`_audit_sentence`/`_backfill`），风险最低；覆盖「看板看不懂」最高频痛点；可让 P2 的速览能力先立标杆。 |
| #2 | 异动 AI 假设解释 | **P0** | 异动检测与维度拆解已成熟（`anomaly/service.py` + `attribution.py`），仅需把结构化事实交给 LLM 出假设；替换固定 `_action_hint` 文案，价值直接；是 #5 的数据源。 |
| #3 | 指标口径 AI 助手 | **P0** | 建指标口径全手写（`MetricAdmin.vue` 的 `calc_notes` 三字段 + 别名），AI 草稿显著降低门槛；有 B13 `_llm_metric_candidates` 传样本值给 LLM 的先例可复用；纯辅助、零入库风险。 |
| #4 | 数据集字段语义标注 | **P1** | 为关系向导与指标建议提供语义数据，是长期价值地基；但非单点用户痛点，可放第二批。需新增列元数据落库与 LLM 标注流程。 |
| #5 | 问数主动推荐升级 | **P1** | 体验增益明显，但强依赖 #2 的「最近异动」数据源；建议与 #2 共用异动摘要结构。 |
| #6 | 归因下钻 AI 解读 | **P2** | 纯增强，依赖下钻树已存在；价值最小、最易收尾，放最后。 |

### 3.1 各需求详细条目

#### #1 看板智能摘要（P0）
- 在 `web/src/views/dashboard/Dashboard.vue` 看板页增加「AI 速览」区块。
- 后端新增接口：收集当前看板周期内各指标卡片的「关键值 + 环比」→ 占位符化（复用 `narrative.py` 的 `_build_ref_table` 与 `PLACEHOLDER_RE`）→ 交 `llm_narrative`/新封装生成 3~5 句速览；必须走 `_audit_sentence` 三道审计，未通过审计的句子剔除。
- LLM 未配置或失败：区块隐藏，或降级为规则化一句式概述（如「本期共 N 个指标，X 个环比上升、Y 个下降」），不报错、不阻塞看板。

#### #2 异动 AI 假设解释（P0）
- 异动触发（`anomaly/service.py` `detect_for_project`）时，自动跑常用维度拆解（贡献最大维度、方向是否一致），作为**结构化事实**（非数字原文）交 LLM 生成业务假设。
- 约束：LLM 只见拆解事实（维度名、方向一致/背离、Top 贡献来源），**不编数字**；输出可引用占位符回填贡献占比。
- 替换/增强通知固定文案 `_action_hint`；指标详情页异动处展示假设。
- 失败降级：保留原 `_action_hint` 固定文案，不展示假设区块。

#### #3 指标口径 AI 助手（P0）
- 指标创建页（`MetricAdmin.vue`）增加「AI 帮写口径」按钮：按「数据集列名 + 样本值」调 LLM，建议 `name`/`aliases`/`calc_notes`（rationale/alternatives/pitfalls）草稿。
- 输出校验：名称/别名须合理、不越权；`calc_notes` 为文本草稿。复用 B13 `_sample_preview` 传样本值的范式（列样本值截断防 prompt 膨胀）。
- 用户可采纳（回填表单）或编辑；**绝不自动入库**，最终由保存动作确认。

#### #4 数据集字段语义标注（P1）
- 数据集上传/接入后，LLM 按「列名 + 样本值」给每列业务含义备注（`semantic_note`）。
- 落库：建议在 dataset 列元数据中新增 `semantic_note` 字段，供关系向导（`_llm_relation_review`）与指标建议（`_llm_metric_candidates`）消费。
- 复用 B13 传样本值给 LLM 的先例；输出须落在真实列名内，防幻觉校验。
- LLM 未配置：跳过标注，关系向导/指标建议退回纯规则（现状不变）。

#### #5 问数主动推荐升级（P1）
- 空态推荐问题（`ask/service.py` `build_suggestions`）从静态规则生成升级为结合「最近异动/趋势」的动态推荐（如「近 7 天日销售额突增，点击查看按渠道拆解」）。
- 复用 #2 的异动摘要结构化数据；推荐文案中的数字**必须经服务端预格式化**（占位符回填），不得直接引用未回填的原始数值。
- LLM 不可用时：退回当前静态规则推荐（现状）。

#### #6 归因下钻 AI 解读（P2）
- 下钻树结果（`attribution.py` `attribute_tree_node` 的 `children` contribution/方向）加一句占位符化 LLM 解读，详情页展示。
- 约束同 #2：只基于拆解事实、不编数字；走 `_audit_sentence` 审计。
- 失败降级：不显示解读句，下钻结果照常。

## 4. 验收标准（含红线）

### 4.1 算写分离红线（叙述类 LLM 调用点必守）
- 新叙述类调用点（#1/#2/#5/#6 涉及文字生成处）必须：① LLM 输入为**占位符清单**（`{{ref:KEY}}` + 业务含义标签），不含原始数值；② 渲染时由服务端预格式化文本回填（LLM 无法篡改）；③ 经 `_audit_sentence` 两道审计——未知 ref 剔句、去占位符后残留数字剔句；④ 章节/整段全被剔除或 LLM 失败 → 降级为规则句或无 LLM 时整段规则句。
- 复用而非重写：`narrative.py` 的 `_build_ref_table` / `PLACEHOLDER_RE` / `BARE_DIGIT_RE` / `_audit_sentence` / `_backfill` 作为统一设施，新功能优先复用。

### 4.2 LLM 可选降级红线
- 所有新功能在 `resolve_llm_config()` 返回 `None`（未配置）或 `chat_json` 返回 `None`（失败/超时）时必须优雅降级，且**不破坏现有无 LLM 体验**：
  - #1 隐藏或降级一句式规则概述；
  - #2 保留原 `_action_hint` 固定文案；
  - #3 按钮禁用/提示「未启用 AI」；
  - #4 跳过标注；
  - #5 退回静态推荐；
  - #6 不显示解读句。
- 任一 LLM 异常不得抛出到用户侧导致页面/接口 500；参考 `chat_json`「任何失败返回 None，调用方降级，不致命」。

### 4.3 展示与名词一致性
- 数字展示统一 1 位小数 + 千分位：指标值用 `formatMetricValue`、百分比用 `formatPercent`（`web/src/utils/format.js`）。
- 涨跌配色：涨=红、跌=绿（中国惯例），由 `TrendBadge` 按变化方向决定，与 good/bad 语义解耦（`trendDirection`）。
- 名词定义引用 `web/src/constants/glossary.js` 单一数据源（异动/要紧度/归因贡献/环比/同比/红涨绿跌/算写分离/常用维度等），禁止在页面另写文案。

### 4.4 结构化输出的防幻觉校验（非叙述类）
- #3/#4 的 JSON 类输出（语义标注、口径建议候选）**不含数字红线**，但必须防幻觉校验：输出字段/值必须落在**真实列名/枚举值/聚合方式白名单**内（aggregation ∈ sum/avg/count_distinct/count/max/min），非法提议丢弃（复用 `modeling/service.py` 的校验范式）。

### 4.5 通用验收
- 每个新功能具备可离线回归的测试注入点（参考 `narrative.py` 用 `monkeypatch` `chat_json` 命名空间，无需 mock HTTP）。
- 权限同源：新建/读取均继承现有 `restricted_metric_ids` 与项目隔离语义。

## 5. 待确认问题

1. **看板速览触发时机**：自动随看板加载生成，还是提供「生成速览」手动按钮（避免每次加载都消耗 LLM 额度）？建议默认手动按钮 + 周期/筛选变化后失效需重生成。
2. **异动假设的解释边界**：是否允许 LLM 结合「业务日历」（促销/节假日）做更丰富假设，还是严格只基于拆解事实（避免引入平台未掌握的外部信息导致臆测）？建议 V1 严格只基于拆解事实。
3. **字段语义标注落库与覆盖**：列备注落在 dataset 列元数据新增 `semantic_note` 字段还是独立表？覆盖全部列还是仅文本/低基数列？建议先覆盖文本列（与关系复审口径一致）。
4. **问数动态推荐的数据隔离**：动态推荐引用的「最近异动」是否受当前项目与用户权限隔离（避免跨项目泄露异动）？建议与问数锁定项目语义一致。
5. **归因解读生成层级**：仅根节点生成一句，还是每一层下钻都生成？建议先根节点 + 用户点击展开的当前层。
6. **LLM 调用预算**：每个新调用点的 `timeout` 与重试策略是否对齐 `chat_json` 默认（30s + 重试 1 次）？建议统一对齐，避免外网不可达时拖垮接口。
